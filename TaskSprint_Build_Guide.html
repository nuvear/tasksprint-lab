Build guide

Target installation: Langflow 1.12.5 on Railway, supplied by the owner. Build edition: 20 October 2026. Delivery status: instructions and seed assets, not a completed deployment.

Start here

The existing Langflow installation is the agent workspace. We will add a small to-do application backend and a bounded function runner, without replacing the existing Langflow service, Postgres database, volume, domain, or credentials.

The five runtime agents are Product Owner Assistant, Scrum Coordinator, Developer, QA, and Production Manager. The story, defect, human release decision, incident, and rollback remain as approved. Build time is separate from the two-hour class.

There are two ways to use this guide. In the coding-assisted route, open this kit in Claude Code or Codex, provide one phase prompt at a time, review its evidence, and perform the private login/credential/deployment steps yourself. In the manual route, implement the same modules and contracts in your editor and follow the same UI steps and checks. The backend sections require Python development; they are not claimed to be achievable by dragging Langflow components alone.

This kit supplies the requirements, runtime prompts, corpus, skills, function fixtures and a read-only preflight script. The service code, control adapters, validated flow exports and most commands below must be produced during the build. Do not run a future-phase command until the corresponding file has been implemented.

Architecture and contracts

A1. Fixed scope and deliberate implementation choices

Preserve the approved story: an existing add/list starter gains task completion; a known faulty candidate deletes the completed task; QA detects this; the Developer repairs it; Operations assesses a release through A2A; a human approves; the app activates the candidate; a candidate-specific incident leads to approved rollback. The classroom is 120 minutes. Preparation has no two-hour constraint.

The following are proposed implementation choices, not claims about features already installed in Langflow:

Decision Implementation
App interface Deterministic commands in Langflow Playground; no separate front end
Application release Atomic selection of an immutable, tested completion-function artifact
Candidate language Small, documented Python subset interpreted by a bounded evaluator
Execution isolation Separate stateless runner service; never Python execution inside Langflow
Knowledge retrieval Metadata-filtered lexical retrieval over a tiny approved corpus; no embedding account needed
Persistent lab data SQLite on a new /data volume, one backend worker/replica, transactional writes
Native protocols Real MCP tools and real Langflow A2A exchange, using the installed protocol versions
Approval Human Input in a protected deterministic flow plus backend approval records
Production scope A synthetic demo-production environment; no live customer or infrastructure operations

The Python-subset decision is important: the Developer writes actual source text, and the runner interprets that source to determine behavior. This is neither unrestricted Python development nor a hard-coded switch between GOOD and BAD. Release is an application-level artifact activation, not a Railway container rollout. Explain both limits to participants.

A2. Services and repositories

Keep nuvear/langflow-railway unchanged unless an explicitly approved compatibility fix is genuinely required. Use a separate proposed repository nuvear/tasksprint-lab. Do not assume it exists or create/push it without the owner approving the action.

Service Role Persistence Exposure
Existing langflow-railway Five model-driven agents, UI, native protocols, checkpoints Existing Postgres and /app/langflow Existing authenticated HTTPS domain
Existing Postgres Langflow-owned data Existing volume Leave unchanged
New tasksprint-lab Trusted app service, MCP, corpus, state, tests, release policy New volume /data Authenticated HTTPS; only minimal /healthz public

The lab uses its own data store, not the existing Langflow database. The runner receives only candidate source and a bounded copy of synthetic task records. A6. Candidate source and bounded execution

Function contract:

def complete(tasks, task_id):
    # tasks: bounded list of JSON dictionaries {id, title, completed}
    # Return {ok: bool, code: str, tasks: list}; do not read or write external state.
    ...

Developer source reads are limited to starter/agent-generated candidates and the explicitly selected faulty fixture needed for repair. Reject Developer source reads of fixture-reference candidates, even when their IDs are known. The trusted test service may execute the reference artifact after a labelled instructor fallback; that does not make its source a Developer retrieval result.

The runner returns a result computed by interpreting this actual source. The lab service validates that result, then commits permissible state changes. The runner never writes the database. The active candidate is resolved by content hash for every command; “deploy” cannot be only a UI label.

Implement a small tree-walking interpreter, not exec with a reduced builtins dict. Allow only the grammar needed by the supplied examples: a single function with two arguments; bounded for loops over supplied lists; if; return; simple assignment; JSON dictionaries/lists/scalars; subscripts; equality/inequality; and a single-level list comprehension. Explicitly reject every unsupported AST node before execution. Use an explicit local-value environment, deep copies at the input/output boundary, and interpreter-owned get/set operations. Never resolve Python attributes or invoke Python callables from candidate syntax. Do not use evaluation of f-strings.

Reject imports, calls, attribute access, dunder names, classes, lambdas, decorators, recursion, generators, while loops, exception machinery, with blocks, named expressions, arbitrary operators, and dynamic code. Function arguments must be exactly tasks, task_id, with no defaults, varargs, kwargs, or annotations.

Initial limits: source ≤4 KiB; ≤256 AST nodes; depth ≤20; input ≤32 KiB; ≤100 tasks; title ≤120 characters; ≤5,000 interpreted operations; ≤2 seconds per evaluation; no unbounded comprehensions or nested iteration. Enforce limits in code, including list creation/output size. A process/request timeout alone is not the boundary. Run as a non-root service. Do not claim Railway blocks all network egress unless that control has actually been configured and tested. The candidate grammar itself must have no networking or filesystem operations.

The trusted runner service may use ordinary Python to implement the interpreter. Candidate source must never become executable Python bytecode or an imported module. This is a constrained training runtime, not a general hostile-code sandbox.

Task operations are idempotent at the app layer. complete on an already completed task leaves its data unchanged. Unknown task IDs return TASK_NOT_FOUND and no mutation. add/list remain trusted server operations and are regression-tested. Use snapshot revision checks when committing a runner response so concurrent writes cannot be silently lost. Serialization is acceptable for this single-presenter lab.

A11. Approval, execution, and rollback algorithm

The human-only TS-90 flow accepts review PLAN_ID, fetches the canonical preview, then pauses at Human Input with Approve/Reject branches. A trusted adapter carries an immutable plan reference across the pause. Approve records a decision through TS_APPROVER_TOKEN; Reject records rejection and never executes anything. Typed chat such as “approved”, a model flag, an Agent Card, or a QA summary is not consent.

The preview shows operation, environment, candidate ID/hash, current and previous hash, application-test evidence, agent-baseline manifest, expected release revision, expiry, and rollback target. A plan hashes all consequential fields and references.

The execution endpoint, in a transaction, must:

  1. Authenticate Operations and check workspace, run status and stop flag.
  2. Check whether this action already has a receipt; return it on an identical replay.
  3. Load the immutable plan and its current, unexpired, unused human approval.
  4. Validate the plan hash, target source hash, environment and release revision.
  5. For deployment, require the exact candidate's protected tests and the approved agent-system manifest. Recompute or verify the evidence, never trust client booleans.
  6. For rollback, require a previously recorded healthy baseline/release and its baseline smoke suite. Do not demand the new feature's tests of the old starter.
  7. Atomically update the active artifact pointer, increment release revision, consume the approval and write the receipt/event. Preserve task records unchanged.
  8. Run post-activation checks separately and record their actual result. A failed post-check is an incident; it is not proof that the transaction never happened.

Use a fifteen-minute approval expiry for the rehearsal unless timings require an explicitly documented change. Changes to source, policy/evidence manifest, plan, environment or active release invalidate the corresponding authorization. Ordinary new task records need not invalidate a release plan; use release revision, not every application-row update, as the release concurrency token.

## Procedure
1. Read the canonical story and current base source. Record their identifiers.
2. Retrieve the current approved requirement passages relevant to the change.
3. Describe the smallest behavior change. Completion retains the target record;

tests/approvals/production. Do not work around a denied capability.

the protected suite evaluates that candidate. Submission alone is not test success.

# TaskSprint product brief

## Product goal
Help workshop participants track a short list of tasks. The interface for this
training app is a deterministic command console inside Langflow Playground.

## Starter
The starter can add and list tasks. Every task has a stable ID, title and completed
boolean. The starter returns FEATURE_UNAVAILABLE for the completion operation.
The starter is the known healthy rollback baseline for this workshop.

## Completion story
As a workshop participant, I want to mark a task complete while retaining it in
my list, so I can distinguish finished work from unfinished work.

## Acceptance criteria
AC1: A known task becomes completed and remains stored with the same ID/title.
AC2: Other task records are unchanged.
AC3: Completing an already completed task is safe and has no additional data effect.
AC4: An unknown task ID returns TASK_NOT_FOUND and changes no task data.
AC5: Add and list continue to work; list includes completed and incomplete tasks.
AC6: Stored records and completion flags survive a backend restart.

## Scope
One completion feature only. No reminders, dates, notifications, authentication
feature development, mobile UI, external emails, or real personal information.
Human Product Owner confirmation is required before treating proposed scope as agreed.

# Definition of Done

## Increment evidence
The implementation is inspectable, identified by immutable source hash, and linked
to the agreed story and retrieved requirements. A protected test suite checks the
candidate's actual behavior on isolated task records. All required application
checks must pass; infrastructure failures are not a pass.

## Agent-system evidence
The workshop agent system has a separately recorded evaluation manifest and
repeated task/trajectory results. Required evidence retrieval, scoped tools,
missing-approval denial, failure escalation and bounded stopping are checked.
Passing application unit tests alone does not establish these properties.

## Acceptance versus release
Human review accepts the increment. Production release is a separate decision
against an exact plan. The team cannot approve its own release, rewrite test results,
or treat a conversational “looks good” as authorization.

## Recovery
The previous healthy application artifact and a tested rollback path are identified.
Application rollback preserves task data. The final state must be described honestly,
including any feature withdrawn by rollback.

# Demonstration release policy

## Environment
Only synthetic demo-production is eligible. Operations never manages Railway,
Langflow infrastructure, billing, provider keys, or non-workshop databases.

## Deployment gate
A release needs exact candidate source/hash, passing protected application tests,
a matching agent-system manifest, a canonical plan and a current human approval
bound to that plan. Approval expires after fifteen minutes in the default workshop
configuration. A changed target, environment, manifest or release revision requires
fresh review. Urgency and agent confidence do not change the rule.

## Execution
Only the Operations identity can execute an approved plan. The backend checks and
consumes approval transactionally and records a replay-safe receipt. A lost response
must be reconciled against external state, not assumed to mean failure.

## Rollback
Rollback needs its own plan and human approval. Its target is a recorded healthy
baseline or prior release. Baseline smoke tests apply to v0; v0 is not expected to
pass the new completion feature tests. Task records and stored flags are preserved.

## Incident drill
Only the human instructor can enable a bounded, candidate-specific application
fault. Service liveness stays healthy. Operations performs explicitly triggered
monitoring cycles; no unattended monitoring service is implied.

These JSON schemas describe TaskSprint data carried inside a supported protocol
part or returned by the application backend. They are **not** Langflow exports,
Agent Cards, A2A protocol envelopes, signed authorizations, or test results.

The builder validates them with format checking enabled. Populate IDs/hashes with
actual service results, never invented example values. The server computes the
release plan hash over the canonical consequential fields, excluding `plan_sha256`
itself. The approve/execute operations load the canonical stored plan rather than
trusting a client reconstruction. Deployment and rollback have different evidence
requirements as described in Architecture A11.

A2A payload packaging must follow the protocol actually advertised by the installed
Agent Card. A text part containing serialized application JSON is acceptable when
the installed implementation supports text artifacts; validate the parsed result.
